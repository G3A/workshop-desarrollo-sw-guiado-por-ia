Plugin sdlc-ia · Fase 3

Ciclo por feature

La fase mejor cubierta del playbook: dos skills la recorren casi entera, de un documento de requisitos a una PR con el CI en verde. El único hueco que queda es la verificación en el navegador.

Especificación

RQSkill

Del requisito de negocio a spec y tareas

/sdlc-ia:requirement-to-spec-java <ruta al documento>. Corre antes de que exista el issue: toma un Word, PDF, Excel o Markdown y detecta qué controladores @RestController, entidades @Entity y migraciones toca el requisito.

Dos cosas que la hacen distinta de pedirle un resumen al agente. Cita, no categoriza: cuando un cambio deja documentación desactualizada nombra el archivo y la línea — «puede que algunos docs necesiten actualizarse» no es un hallazgo. Y nunca inventa: un adjunto que no se pudo abrir se reporta como no leído.

El destino siempre se pregunta: un issue de GitHub con un sub-issue nativo por tarea, o docs/specs/<slug>/spec.md más tasks.md. Si es GitHub, también pregunta a qué milestone —el sprint— con «ninguno, queda en el backlog» como primera opción, porque meter un issue en un sprint es una decisión de planificación tuya.

La frontera es lo que la hace segura de correr temprano. Nunca escribe código, nunca abre PR, nunca toca git. Se puede correr sobre un documento que todavía nadie aprobó.
Fuente: requirement-to-spec-java/SKILL.md, fases 1 a 6; visor, nodo r1.
S1Skill

Toma el issue del sprint

/sdlc-ia:github-plan-build <número o URL>. Lo primero que hace es traer el issue completo —título, cuerpo, comentarios, etiquetas— porque muchas veces los requisitos reales están negociados en los comentarios, no en el cuerpo original.

Como GitHub no tiene campo de estado nativo, detecta si el repositorio marca «en progreso» con etiquetas o con GitHub Projects v2. Si encuentra los dos, pregunta una sola vez cuál es la fuente de verdad en vez de escribir en ambos; si no encuentra ninguno, salta esos pasos y lo deja anotado, para que «se saltó» no se confunda con «se olvidó».

Armar el sprint es tuyo. Sin milestones y sin tablero, «tomar issue del sprint» no tiene dónde mirar. El visor lo cubre en el nodo pj.
Fuente: github-plan-build/SKILL.md, fases 1 y 2; visor, nodos pj y bo1.
S2Skill

Plan y revisión adversarial

Pasos B a D del ciclo de construcción: preguntar lo que el issue dejó abierto en materia de diseño con opciones concretas, explorar el repositorio (con subagentes en paralelo si el cambio toca varias áreas), y redactar un plan paso a paso cuyo primer paso siempre es una prueba que falla.

Después, el plan pasa por una revisión adversarial desde tres ángulos —convenciones del repositorio, corrección y alcance— antes de escribir una sola línea de código.

Antes de nada, la fase 3 prepara git: resuelve la rama de integración que declare AGENTS.md (en este monorepo, dev), la sincroniza, confirma que el árbol está limpio y crea <prefijo>/<número>-<slug> con el prefijo que el repositorio ya usa.

Fuente: github-plan-build/references/build-loop.md, pasos A a D; visor, nodo c1.
S3A mano

Aprueba el plan

El punto de aprobación es condicional: la skill solo entra en modo plan si el cambio es grande, toca un contrato público, un esquema de datos o permisos, o si la revisión adversarial dejó algo sin resolver. Si el cambio es chico y reversible, sigue directo.

Una vez aprobado, publica el plan como comentario en el issue —pasos, decisiones, supuestos y lo que queda fuera— para que el equipo lo lea sin abrir una sesión del agente.

Aprobar sigue siendo decisión tuya, y el visor insiste en por qué: «el plan lo escribió el agente, pero la responsabilidad de que tenga sentido es de quien lo aprueba». Su nodo G3 tiene tres salidas, no dos: seguir, ajustar, o descartar.

Si quieres el checkpoint siempre, pídelo explícitamente. Si quieres uno más, confirm-push agrega una pausa entre el commit y el push, y te deja los comandos exactos si eliges detenerte ahí.
Fuente: github-plan-build, paso E; visor, nodos bo2 y G3.
S4Skill

Tareas verificables

El contrato con el agente. Cada tarea tiene que ser del tamaño de un commit; si es más grande, se desglosa ahí mismo, no se deja para después. Es la misma regla en las dos skills de entrega, y es lo que hace que el historial se lea tarea por tarea en vez de como un único commit gigante al final.

Fuente: requirement-to-spec-java/SKILL.md, «Decisiones de diseño»; github-plan-build, paso F.

Implementación

I1Skill

Implementa con test primero

Paso F: en pasos pequeños, corriendo el gate acotado después de cada uno y haciendo un commit por paso en verde con Refs #<n>. El commit que completa el último paso lleva Closes #<n>.

La skill no asume ninguna arquitectura: no revisa ni recomienda Clean Architecture, hexagonal ni MVC. El plan sigue lo que el repositorio ya hace.

Fuente: github-plan-build/references/build-loop-execute.md, paso F; visor, nodo c2.
I2Skill

Gates locales

El gate acotado después de cada paso, y los gates completos del repositorio —lint, build, tests— antes de abrir la PR. Los comandos más comunes vienen preaprobados (make, mvn, gradle, npm, pytest, entre otros).

Una regla explícita que vale la pena conocer: si el gate del repositorio no está en esa lista, la skill igual lo corre y acepta el permiso que aparezca — nunca se salta ni simula un gate para evitar el diálogo de confirmación.
Fuente: github-plan-build/SKILL.md, «Decisiones de diseño».
I3Skill

Revisión del agente, antes de abrir la PR

/code-review siempre; /security-review si el cambio toca autenticación o entradas externas. Las dos corren en tu máquina y cuentan contra el uso normal de tu plan.

Dos precisiones. El comando se llama /code-review (/review sigue funcionando como alias). Y /security-review busca vulnerabilidades, pero no las clasifica por CWE.
Fuente: github-plan-build, paso G.
UI

¿La tarea tiene interfaz?

Si no, salta directo a la verificación en 4 capas. Si sí, hay dos pasos más, y los dos están mal cubiertos: es la rama más débil de esta fase.

El visor lo dice sin rodeos en su nodo GUI: «un test automatizado puede confirmar que un componente renderiza — no puede confirmar que se ve bien».

V0A mano

Vista previa efímera por PR

Verificar contra una URL real y compartible es más confiable, y más fácil de mostrarle a alguien, que correrlo solo en tu máquina. El mecanismo exacto depende del stack: la idea es que cada PR con cambios visuales tenga su propia URL descartable.

Fuente: visor, nodo v0.
VWHueco

Verifica en el navegador

El método pide que el agente mire el resultado con sus propios ojos: Playwright MCP, Chrome DevTools MCP o Claude for Chrome, para que pueda navegar la pantalla que acaba de construir antes de decir que terminó.

Qué falta. Ninguna skill del plugin registra ni maneja esos servidores — instrument-agent-java ofrece GitHub, Context7 y DBHub, ninguno de navegador. Y el hueco viene de arriba: sin los design tokens ni el COMPONENTS.md de la caja X4, tampoco hay contra qué comparar lo que el navegador muestre.
La parte humana no es un hueco. El visor la cubre en su nodo vw, y la deja deliberadamente manual: es la parte del proceso donde «se ve bien» todavía no tiene una forma barata de automatizarse del todo.

Verificación en 4 capas

VL1Skill

1 · Local

El agente rompe lo obvio antes de subir: los hooks de pre-commit, los linters y los tests que instrument-project-java dejó instalados corren en tu máquina, no en el pipeline. Rápido, pero corto de alcance — por eso hay tres capas más.

Fuente: github-plan-build, paso F; visor, nodo c3.
VL2Skill

2 · CI, el juez

Abrir la PR es lo que dispara el juez. La skill la abre enlazando el issue con el token de cierre (Closes #<n>), y después vigila la corrida hasta que quede verde y atiende los comentarios de revisión uno por uno.

Tiene un límite explícito para no quedarse dando vueltas: escala a una persona si un fallo de CI es ambiguo (no se sabe si es intermitente o real) o si un ciclo de arreglos no converge después de tres intentos sobre el mismo job.

Esta capa depende de la caja DCJ de la Fase 2. Si el Ruleset no exige el check, el «juez» opina pero no bloquea.
Fuente: github-plan-build, pasos H e I; visor, nodos p1 y G5.
VL3Parcial

3 · Seguridad

Lo que sí hay: /security-review sobre el diff, y OWASP Dependency-Check detrás de make sca, que falla make ci con CVSS ≥ 7 — si el control 9 quedó encendido, que no es el default.

Qué falta. El SAST del código propio (SpotBugs con FindSecBugs) y el DAST. Hoy la capa cubre dependencias de terceros y una revisión por modelo; no cubre un análisis estático de seguridad sobre el código que el agente acaba de escribir.
VL4Skill

4 · Revisión humana

La capa que ninguna de las otras tres puede reemplazar. El método la define como un checklist concreto de qué mirar en un diff que escribió un modelo:

  • Alucinaciones de API — métodos y firmas que suenan bien y no existen.
  • Fidelidad al proyecto — ¿resuelve como este repositorio resuelve, o como resuelve internet?
  • Tests de la spec — ¿las pruebas verifican el requisito, o verifican lo que el código hace?
  • Deuda técnica — qué quedó peor para que esto quedara listo.
  • Trade-offs — qué se decidió sin decirlo.
  • Corre el cambio tú mismo — el paso que más se salta.

/sdlc-ia:agent-context-java los escribe en REVIEW.md —quince ítems concretos bajo esas seis categorías— y deja una plantilla de PR con las seis como casillas, que aparece sola en el momento de revisar.

De dónde sale cada mitad, dicho sin adornos. Las seis categorías son del método. Los quince ítems concretos los redacta la plantilla de la skill: son la forma accionable que se les da, no una cita de ninguna fuente — y la skill lo dice así al reportar, invitando al equipo a cambiarlos.
Las casillas no son un check de CI, a propósito. Exigirlas convierte el juicio humano en trámite: se marcan las seis sin mirar y el registro empieza a mentir. Dejan rastro de qué se revisó; no lo garantizan.
La lista evoluciona en los dos sentidos. Lo que dices a mano por tercera vez en una revisión es un criterio que falta en REVIEW.md. Y al revés: un criterio que una máquina pueda comprobar deja de ser texto y se vuelve sensor — si sigue siendo prosa, es trabajo manual que alguien repite en cada PR.
Fuente: agent-context-java/SKILL.md, fase 4; templates/es/REVIEW.md.template; visor, nodo cr para el porqué de la capa.
GV

¿Aprueba la verificación?

Este gate es sobre criterios de aceptación, no sobre si el código compila — eso ya lo respondió la capa 2. Si no aprueba, se replantea solo la tarea que falló, no el issue entero: es más barato y deja el resto del trabajo en pie.

Fuente: visor, nodos G4 y c4p.
M1Skill

Merge, con el PR marcado como asistido por IA

Cada commit que la skill hace, y el cuerpo del PR, terminan con el trailer Asistido-por-IA: <modelo>, con el id del modelo que corrió la sesión. Va en los dos lugares a propósito: así sobrevive a un squash merge que tome el cuerpo del PR como mensaje del commit.

Eso deja el repositorio con una consulta que separa lo asistido del resto:

git log --format='%(trailers:key=Asistido-por-IA)'
El merge lo corres tú. La skill nunca hace merge, nunca activa auto-merge y nunca despliega. Es el Ruleset el que habilita o bloquea el botón.
Guarda este dato para la Fase 5. Es la única de las cuatro métricas cuyo insumo ya está escrito en cada commit — y nadie lo lee todavía.
Fuente: github-plan-build, paso G; AGENTS.md del monorepo; visor, nodos mg y G6.
MF

¿Quedan más issues del sprint?

Si sí, vuelve a tomar uno. Si no, sigue a la retroalimentación — que es el paso que hace que la vuelta 20 sea más fluida que la vuelta 1, y el que más se salta cuando el sprint viene apretado.

Fuente: visor, nodo G7, el cierre del ciclo PDCA.
