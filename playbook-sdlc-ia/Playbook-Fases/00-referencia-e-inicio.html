RB

Los 5 badges de cobertura

Cada caja del diagrama lleva uno. El badge no juzga la importancia del paso: dice quién lo ejecuta hoy y nada más.

Skill La corre el plugin, con su comando. La caja nombra cuál.

Parcial Hay una skill que toca el paso, pero no lo cubre entero. La sección dice exactamente qué queda afuera — ese resto es un hueco con nombre.

A mano Lo haces tú, y el repositorio te enseña cómo: un nodo del visor proceso-operacional-con-ia, o un manual de manuales/. No es un hueco: es un paso que a propósito no se automatizó.

Hueco Nadie lo cubre en este repositorio: ni skill, ni visor, ni manual. Cada uno de estos es trabajo que todavía no tiene issue.

Fuera de alcance Frontera declarada del plugin, no un olvido. El README.md las nombra: Azure DevOps, memoria semántica entre sesiones, y un panel de agentes especialistas por stack. Y una derivada: los hooks type: mcp_tool, cuyo único caso de uso aquí era esa memoria.

Un parcial es más peligroso que un hueco, por la misma razón que un control de instrumentación a medias: el equipo cree que ya está cubierto y deja de mirarlo.
RDEl eje

El eje de la instrumentación

Un control es determinista solo si el disparo y la decisión quedan los dos fuera del razonamiento del modelo. Basta que una de las dos dependa del modelo para que sea no determinista.

El eje es quién dispara y quién decide, no cómo está implementado. Por eso los nueve hooks de comando que instala instrument-agent-java son deterministas —el ciclo de vida del agente los dispara en un punto fijo, y un script de shell decide— mientras que los servidores MCP que la misma skill registra son no deterministas: el modelo decide cuándo llamarlos y con qué argumentos.

Dos excepciones que rompen la intuición. Un hook type: mcp_tool es determinista, aunque llame a un servidor MCP, porque el modelo no eligió llamarlo. Y un hook type: prompt es no determinista, aunque sea un hook, porque la decisión sale de inferencia.
Fuente: la leyenda de proceso-operacional-con-ia/comandos.json (instrumentacionTipos), que cita la documentación de Claude Code y la especificación de MCP.

Selecciona el repositorio

Brownfield, Java con Maven. El plugin está afinado para eso: instrument-project-java lee el JDK y la versión de Maven del wrapper y del POM, y agent-context-java confirma que es un repo Java antes de hacer nada.

Antes de seguir, el visor te hace dos chequeos que conviene no saltar: el nodo f0 confirma que el equipo ya tiene las cuatro prácticas base funcionando sin el agente, y el nodo G1 comprueba que la instalación quedó sana.

IPSkill

Instala el plugin en tu máquina

Un solo comando, desde la carpeta del plugin, en cualquier equipo que tenga el clon:

.\update.ps1        # Windows PowerShell 5.1 o PowerShell 7
./update.sh         # macOS, Linux, Git Bash

Hace git pull --ff-only sobre la rama en la que esté el clon, registra el marketplace si falta o apunta a otra ruta, refresca e instala, y verifica que la caché instalada sea idéntica a la fuente archivo por archivo.

Por qué hace falta un script. La CLI instala el plugin copiándolo a una caché, y claude plugin install nunca refresca un plugin que ya figura instalado, ni siquiera cuando plugin.json subió de versión. La única forma de traer la copia nueva es desinstalar e instalar, y eso es lo que hace el script.

Los cambios aplican a las sesiones nuevas de Claude Code; una sesión abierta sigue con las skills que cargó al arrancar.

Fuente: instrumentacion-java-ia/README.md, sección «Actualizar cuando sale una versión nueva», y su AGENTS.md.
