1Fundamentos de colaboraciónnodo f0

Un agente de IA no arregla un equipo sin estas prácticas: las amplifica. Si nadie revisa código, el agente va a mergear más código sin revisar, más rápido. Estos cuatro fundamentos son del equipo, no del agente — si falta alguno, la conversación es con tu equipo, no un paso que puedas resolver solo/a.

Evidencia real

Control de versiones con Git: real, historia genuina. Pull Requests: real — PR #2, #4, #5 y #6, las cuatro mergeadas — nadie pushea directo a dev. Revisión de código: parcial, con honestidad — repo de un solo colaborador; lo que sí hubo fue una pasada real de /code-review antes de pedir el merge (actividad 27), que encontró y corrigió dos bugs reales. Documentación base: real — README.md, AGENTS.md, CLAUDE.md ya en la raíz del repo.

3Dominar los 4 gestos basenodo fd2

La mayoría de la fricción con un agente de código no es del agente — es de no saber los cuatro gestos que controlan qué hace y cuándo. Sin esto, cualquier sesión se siente como una caja negra impredecible.

Evidencia real

Los cuatro se usaron de verdad en este mismo ciclo: @menciones (cada archivo tocado se leyó por ruta real antes de editarlo — Orquestador.java, ChatController.java, etc.); modo plan (la implementación completa se planificó en modo plan antes de tocar código — ver actividad 18); permisos (cada git push y gh pr merge pidió su propia autorización); puntos de control (un git stash deliberado para reproducir en rojo un bug antes de confiar en el fix — ver actividad 27).

6Configurar MCP de ejemplonodo a2instrumentación no determinista

Dos tipos de instrumentación, no uno solo — se distinguen desde acá porque las actividades 9–13 dependen de la diferencia: determinista (etiqueta azul, la instala instrument-project-java) son controles que deciden en milisegundos, con el mismo resultado siempre que las mismas entradas — build estricto, Checkstyle, ArchUnit, CI. No determinista (etiqueta naranja, la instala instrument-agent-java, este mismo nodo) son controles cuyo motor es inferencia, no cómputo — aplican criterio en el momento: ¿esto es un secreto real?, ¿este comando es peligroso?

Esta skill hace en un solo paso lo que antes describíamos a mano: registra los servidores MCP que tu equipo necesita (con las versiones fijadas, nunca "la última" sin pinear) y activa un catálogo de hooks de Claude Code que limitan lo que el agente puede hacer solo — leer un archivo de secretos, correr un comando peligroso, editar una migración ya aplicada. Es la skill real instrument-agent-java del paquete instrumentacion-java-ia/ de este mismo taller: puedes leer su código completo, no es una caja negra.

Evidencia real

Ya aplicado antes de esta sesión: .mcp.json registra ark_github (servidor oficial de GitHub) y ark_dbhub (Postgres, versión @1.2.1 fijada); .claude/settings.json ya tiene el catálogo de hooks (secret-read-guard, dependency-sweep, entre otros).

Brecha no verificada en esta sesión: no se confirmó si GITHUB_PAT/APP_DSN están configuradas — no se tocó .env.

Esto reemplaza lo que en otras plataformas se arma con "políticas de rama": acá el mecanismo es un Ruleset (la forma recomendada actualmente en GitHub, por encima de las reglas de protección de rama clásicas — es a nivel de organización, con lista de excepciones auditable). Evidencia real

Ya configurado antes de esta sesión — issue #1, PR #2, mergeada. El Ruleset dev - CI + revision exige el workflow CI en verde y 1 aprobación.

Corrección de taxonomía, encontrada en esta misma revisión: este nodo estaba etiquetado "madurez": "2" ("Instrumentación no determinista") en comandos.json, pero instrument-project-java es, por su propia descripción, la skill que instala la instrumentación determinista. Corrección de orden, encontrada en esta misma revisión: esta actividad estaba ubicada después de "Verificar que llegó el arnés"/"Activar hooks locales" (siguientes dos actividades) — pero instrument-project-java (este nodo) es quien escribe lefthook.yml en el repo. Lo que sí se encontró de nuevo en este ciclo (actividad 28): el Ruleset nunca tuvo un bypass actor configurado — en un repo de una sola persona, eso bloquea cualquier merge para siempre, porque nadie puede aprobar su propia PR.

12Activar hooks localesnodo b4instrumentación determinista

Un hook que existe en el repo pero no está instalado en tu máquina no hace nada — este paso es el que realmente lo activa localmente.

Evidencia real

Este paso activa solo el arnés de Git (lefthook install) — no solo instalado: disparado de verdad siete veces durante esta sesión — el pre-commit corrió gitleaks y Spotless en cada uno de los 8 commits reales de este ciclo, y el pre-push corrió make check completo antes de cada uno de los 4 git push (bloqueó uno, por JDK equivocado — ver actividad 21).

Lo que este paso NO hace: activar los hooks del agente. Esos no se "instalan" — quedan activos apenas .claude/settings.json los declara, incluso recién clonado el repo. Confundir "activar lefthook" con "los hooks del agente ya funcionan" es justo el hueco que la actividad siguiente cierra.

13Confirmar hooks del agentenodo b5 — nuevo, agregado por esta misma revisióninstrumentación no determinista

Un hook del agente que existe en .claude/settings.json pero nunca se vio disparar en esta máquina concreta no es un hook — es una promesa. A diferencia de lefthook, no hace falta instalarlo: hace falta probarlo, disparándolo de verdad, porque la ruta al intérprete de shell, las rutas de archivo, o el propio antivirus pueden variar entre tu computador y el de quien lo configuró originalmente.

Evidencia real

La skill instrument-agent-java (actividad 6) ya prueba esto una vez, al instalar los hooks — su Fase 5, "verificar rompiendo": dispara cada hook a propósito y revierte. Pero esa verificación la corre quien configura el repo, no necesariamente cada persona que lo clona después. En esta sesión no se instaló ningún hook nuevo, así que no hubo nada que volver a disparar — el gap real que sí se encontró es otro: este chequeo nunca existió como un paso propio y explícito del camino feliz, separado de "activar lefthook" (actividad 12). Quedaba implícito dentro de la actividad 6, y por eso no quedaba claro leyendo solo la lista. Se agregó como nodo nuevo (b5) tanto en este manual como en el diagrama BPMN del proceso operacional, justo después de "Activar hooks locales".

24Commit con pie Closes #N (con los criterios de aceptación cumplidos)nodo c4b

El pie Closes #123 es la convención nativa de GitHub para enlazar un commit a un issue — cuando el commit llega a la rama principal, GitHub cierra el issue solo. Es lo contrario de lo que pediría una plataforma de work items separada: acá el commit y el issue son parte del mismo grafo.

Evidencia real

Los 6 commits de esta rama usaron Refs #3, no Closes #3 — el Closes #3 se puso en el cuerpo de la PR (actividad 26), siguiendo la convención de que el cierre lo dispare el merge, no cada commit individual.

Esto tuvo una consecuencia real (ver actividad 28): el squash del merge tomó el mensaje por defecto, no el cuerpo de la PR, así que el Closes #3 nunca llegó al commit real que quedó en dev — el issue no se cerró solo.
